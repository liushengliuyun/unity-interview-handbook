# 第 3 章 死代码扫描与清理

## 模块背景（开场一句话）

> 我做过全工程死代码扫描与分批清理：Lua 侧识别死文件 71 个、空壳 43 个、生成残留 151 个，C# 侧识别 33 个、疑似 21 个。这项工作的面试价值在**方法论**——动态语言死代码判定是普适难题，"静态扫描找全 + 运行时验证证实"的双轮法可迁移到任何动态语言项目。

## 高频问题与回答要点

### Q1: 死代码为什么要清？留着不行吗？

**先立论再讲做法：**

- **认知成本**：死代码是负资产——读代码的人要花时间判断"这有人调吗"，团队越大越贵。
- **误导修改**：改功能时容易改到无人使用的分支，浪费并引入回归风险。
- **热更脚本体积**：本项目 Lua 全热更，脚本体积直接进热更包。
- **下线残留堆积**：下线玩法（美女/故事系统，69+1 文件删除 + 68 个 lua 大改）若不清，下一个下线玩法继续堆。
- **生成物残留**：Luban 导出物中源表已删的死表残留 11 个，误导查表。

### Q2: Lua 是动态语言，死代码怎么判定？（核心题）

**先讲难点**：C# 可靠编译器/IDE Find Usages，Lua 不可 100% 静态判定——加载点可以是字符串拼接、配置驱动加载、FSM 状态拼接、UI 名即文件名，任何字符串间接层都会漏判/误判。

**我的方案：动态加载点清单法**

1. **枚举动态加载点清单**（关键创新，面试重点讲这里）：把全工程"通过字符串间接找到文件"的加载点枚举成清单：
   - UI：`UIManager:OpenUI(name)`，UI 名即文件名，还有 FairyGUI 组件名。
   - Scene：场景脚本文件名=场景名。
   - 配置驱动：引导配置引用文件名。
   - FSM 状态拼接：`"MainBuildingBubbleStates." .. stateName` 字符串拼接类名。
   - 反射（C# 侧）。
2. **双验证规则**：0 引用 **且** 不在任何动态加载点覆盖范围内 → 判死。
3. **C# 侧加类名+GUID 双验证**：.meta 的 GUID 可能被 prefab/asset 引用。
4. **分批清理**：逐批 commit 注明行数与验证方式（如"删除 NamePool.lua（3008 行，全工程 0 引用）"），出现回归可单批回滚。
5. **扫描脚本可复跑**：dead_code_scan.js / dead_code_classify.js / dead_code_final.json 保留在 .omc/artifacts，2026-09-30 基线可复跑比对。

**TSD 加密环境特有约束**（详见第 9 章，此处一句带过）：bash 裸 grep 看到的是密文，node/git 看明文——**扫描脚本必须用 node 写，"工具选型受环境约束"本身就是面试素材**。

### Q3: 怎么防误删？

- **双验证**：0 引用 + 动态加载点清单覆盖；C# 加类名+GUID 双验证。
- **分批清理**：逐批 commit 注明行数与验证方式，回归可单批回滚。
- **回滚预案**：靠 git 回滚，不靠临时备份（备份会漂移，git 保真）。
- **生成物不手改**：Luban 导出物只经导出管线变更，防"源表删了生成物残留"误导。
- **删前复跑**：删除前复跑扫描并比对基线。

### Q4: 清理收益怎么量化？

- **脚本体积**：Lua 全热更，脚本体积直接进热更包，清理=直接收益。
- **认知成本**：71 个 0 引用文件 = 71 次"这有人调吗"的判断成本清零。
- **生成残留**：11 个死表残留清掉后查表不误导。
- **大文件案例**：NamePool.lua 3008 行 0 引用、promise_spec 1620 行框架测试 0 引用、FairyBook 610 行 0 引用。
- **严谨句式**：**"识别 ≠ 已清理"**——C# 识别 33 + 疑似 21 是识别数，不是全部已清数。

### Q5: 怎么防"清了又长"？

- **源头治理**：玩法下线时同步清代码（美女/故事系统下线同步改 68 个 lua）。
- **保留兼容层**：下线时保留必要兼容常量（GIFT_SHOP_BUILD_BEAUTY、EXPLORE_PARAMETER_FUNGUS），兼容层也要有"何时可删"的判断。
- **定期大扫除模式**：当前是人工定期扫，未进 CI——如实承认，引出优化方向。

## 深水区追问

### 追问 1: 静态判定会不会有假阴性？

会。字符串间接层的存在使静态判定必然保守（宁可漏判不误删）。三重对策：动态加载点清单尽量穷举、扫描脚本可复跑（新代码进来后重扫）、删后观察期（分批提交本身就是观察期）。

### 追问 2: 为什么不直接用现成工具？

- Lua 有 luacheck（本项目在用）但只查未定义全局/未使用局部，不查文件级 0 引用。
- 商业工具不覆盖"配置驱动加载"这种项目自定义间接层。
- 自研扫描器一天写完，且**加载点清单是项目知识，工具复用的是知识而非代码**。

### 追问 3: C# 死代码为什么不全部清理？

- 疑似项 21 个涉及反射调用可能（C# 反射按类型名字符串可命中任何类），需要逐个运行时验证，风险收益比不划算。
- 如实回答"识别了但未全清"，展示对风险收益比的判断。

## 优化方向（本模块）

1. **扫描进 CI**：每次合入后自动重扫，新增死代码 PR 阶段报警（替代"定期大扫除"）。
2. **动态加载点清单文档化**：从"我脑子里的清单"变成仓库内文档，团队可维护。
3. **配置侧联扫**：把配置表引用（引导配置/FSM 配置）纳入扫描输入，减少人工核对。
4. **清理自动化**：0 引用文件自动生成删除 PR，人工只做确认。

## 本章核心记忆点

- 难点：动态语言死代码判定不可 100% 静态——字符串间接层（UI 名/场景名/FSM 拼接/配置引用）。
- 方案：动态加载点清单法 + 双验证 + 分批清理 + 脚本可复跑。
- 基线数字：Lua 死 71 + 空 43 + 生成残留 151；C# 死 33 + 疑似 21。
- 亮点句 1："工具选型受环境约束"（TSD 加密下 bash grep 看密文、node 看明文）。
- 亮点句 2："识别 ≠ 已清理"——严谨性句式。
