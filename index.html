前言：这本手册怎么用

本手册基于 SVS 项目（Unity 3D 手游，C# + XLua + FairyGUI + HybridCLR + YooAssets）中实际做过的模块整理，每一章对应一个可以独立展开讲 15~30 分钟的模块，结构统一为：

  • 模块背景：一句话让面试官知道你负责什么、规模多大。
  • 高频问题与回答要点：面试官最可能问的问题，以及回答时应覆盖的关键词。
  • 深水区追问：进阶面试官会追的第二层、第三层问题，以及深度回答思路。
  • 优化方向：被问"你觉得还能怎么改进"时的储备弹药。

使用原则

  1. 先讲结论，再讲细节。任何问题的第一句回答给出定性结论（"这个问题本质是 X"），细节按追问逐层展开，不要一次性倾倒。
  2. 所有回答必须落在你真实做过的事上。手册中的案例都来自真实提交，引用时给出 commit 号可以增强可信度（面试时口头说"我记得当时的提交是……"即可）。
  3. 不会的题回到方法论文上。没做过的方向，用"我们项目当时的做法是……如果换成 X 方案，我会考虑……"的方式借力打力。

第 1 章 BI 打点体系与 Adjust 归因

模块背景（开场一句话）

我负责项目 BI 埋点客户端侧的体系化改造和 Adjust 归因全链路接入。埋点侧把散落的打点统一到 base_bi 配置表驱动 + BtnClickRequest 统一通道；归因侧从协议字段、归因轮询桥、设备 ID 上报双通路到编辑器模拟链路都是我做的，中间踩过 HybridCLR 热更时序、ServiceLocator 门禁等深坑。

高频问题与回答要点

Q1: 你们项目的埋点体系是怎么设计的？

要点式回答：

  • 三层结构：业务层只负责"发"，中转层统一收集，配置层定义"发什么"。
  • 配置表驱动：所有打点定义在 base_bi 配置表（Luban 导出为 Lua，defaultValues 元表——等于默认值的字段导出时省略，不能误判为字段缺失）。每个事件一行，含事件名、参数、bi_args 中文描述。
  • 统一通道：按钮点击类打点走 BtnClickRequest，btn_name 由"事件名+cn 中文描述+extra 扩展参数"拼接，服务端做落库与分发（Adjust / 自有 BI）。
  • 事件码体系：BI_EVENT 常量 + base_bi 表场景/行号映射。打点代码只传事件码与参数，命名如 FpsGuideResult_Win_关卡id、FpsFailGoto。
  • 为什么这样设计：打点是策划/运营强依赖的，表驱动让运营侧可自助查口径，程序侧只需维护"接线"，改动集中在数据侧。

Q2: 打点需求来了，你的完整工作流是什么？

  1. 口径确认：和策划确认事件语义（触发时机、参数、去重口径）——先对齐"什么时候算 Win"，再写代码。
  2. 表侧：改 Excel 源表（prj_config），导出 Luban → Assets/Luban 只读，永远不直接改导出物。
  3. 代码侧：在业务触发点 fire BI_EVENT，把参数（关卡 id、cn 描述）带进 BtnClickRequest。
  4. 真机验证：Adjust 后台看实时日志，确认 token/事件/参数三对。
  5. 存档：维护权威对照表（adjust_android_event_mapping.xlsx，3 个 sheet：事件↔token↔通道对照、发送状态、不发送原因分类：type11 仅 AF、type22 代码注释、无调用点等）——157 行能发出、47 行不发且逐行有原因，这个数字本身就是面试加分项。

Q3: Adjust 归因是什么？你们怎么接的？

概念层：Adjust 是移动归因平台，负责"用户从哪个广告渠道来"。核心链路：SDK 初始化 → 归因数据（tracker/network/campaign/creative）→ 客户端把归因结果随登录上报给服务器 → 服务器侧按渠道做运营配置（首充/活动）。

我们的实现层：

  • SDK 非热更程序集，归因轮询逻辑在热更侧——所以轮询不能在 boot 阶段启动，必须等 HybridCLR 热更 dll 加载完成后再启动，否则反射拿不到桥接方法。
  • 桥接设计：C# 桥提供 GetAdjustAttribution / FetchAdjustAttribution，Lua 侧经 ServiceLocator 门面调用，宏切换真机（真机调 SDK）/编辑器（PlayerPrefs 模拟归因数据，全链路可离线调试）编辑器（PlayerPrefs 模拟归因数据，全链路可离线调试）。
  • 登录上报双通路：① 随 Adjust 归因推送（等归因到达）② UpdateDeviceIds 读到即推（idfa/adjustid 读到就先推）。HttpLogin / LOGIN / SetLoginNewChannel 三处协议都带设备标识字段，避免单通路失败导致服务器侧缺失。
  • 字段演进：NewChannel 取值从 tracker_name 改为 network（tracker_name 只能表达"哪个链接"，network 才表达"哪个渠道平台"）——这类口径变更要同步通知服务器/运营。
  • GM 参数覆盖：测试期可通过 GM 参数覆盖归因结果（内聚到 SDKManager:GetAdjustFromParams 单点），避免测试账号被真实归因污染。

Q4: 你们怎么验证打点/归因到了？

  • Adjust 后台实时日志按设备标识过滤，核对 token、事件、渠道参数三项。
  • 服务器侧落库后 BI 平台查数。
  • 编辑器模拟链路：编辑器下用 PlayerPrefs 模拟归因结果，可在没有真机的情况下验证登录上报链路逻辑。

深水区追问

追问 1: 为什么归因轮询不能在 boot 启动？

这是本项目最值得讲的时序深坑，标准答案分四层：

  1. 背景：HybridCLR 热更程序集与 AOT 獲补元数据机制——Adjust SDK 在非热更程序集，桥接方法在热更程序集。
  2. 现象：boot 阶段启动轮询 → 反射/服务发现拿不到桥 → 归因永远取不到。
  3. 根因链：boot → LoadDll（热更 dll 加载）→ ServiceLocator 注册热更服务 → 之后 Lua 才能调用。任何"登录期就调 GamePlayCore 服务"的代码都会在这里报 Service type not found。
  4. 解法与泛化：引入 DllEntry 门禁：热更程序集加载完成时置位 _G.Root.DllEntry（C# 侧），所有登录期服务调用以此为就绪信号。这个门禁后来泛化成登录期时序的统一解——归因轮询、AutoShrink 就绪信号、编辑器 QuickLoader 黑屏（编辑器启动时 DllEntry 回调置位 Root.DllEntry）都靠它修好。面试点：把一个 bug 修复泛化为架构级的就绪信号门禁。

追问 2: 打点不准确怎么办？如何保证打点质量？

  • 口径先行：事件语义与策划/服务端对齐后才写代码（实例：打点 39 教学完成打不上，根因是 Config431 指向不存在的引导 ID 201104，IsTriggerComplete 恒 false——配置侧口径错了，下游代码怎么写都没用；此案例当时是定位到根因后挂起等口径方）。

打点 39 教学完成打不上：根因是配置指向不存在的引导 ID，下游 token 配对了也没用，挂起等口径方确认。

  • 映射表存档：token ↔ 事件 ↔ 通道的权威对照表 + 每行"能发/不能发及原因"，运营侧口径混乱时直接甩表。
  • 发送状态盘点：定期盘点 base_bi 全表发送状态（157 能发 / 47 不发、原因分类），保证"表里有的都能发，发不出的知道为什么"。

追问 3: 如果要你重新设计埋点系统，你会怎么设计？

  • 上报通道合并：当前 BtnClickRequest 是复用按钮点击协议承载所有 BI 事件，语义上是"搭车"，存在字段挤占与限流耦合——重新设计会拆出独立 BI 上报协议，支持批量上报与丢失补偿（本地缓存 + 恢复网络后补发）。
  • 客户端校验：导出 Lua 时同步生成"参数 schema 校验"（事件参数类型/必填检查），开发期在编辑器 log 警告而非线上静默丢参。
  • 灰度与开关：打点开关按渠道/版本下发，可一键关停异常打点。
  • 私域属性：用户隐私合规（GDPR/国内个保法）要求打点字段最小化，建议打点字段评审时加合规评审。

追问 4: 归因数据会被伪造吗？

会。客户端归因结果可以被改机/改包伪造（改机工具可篡改 Adjust SDK 回调），所以归因数据只能用于运营配置下发依据，不可作为结算/发奖依据——发奖类逻辑必须以服务器自有证据（设备标识+行为风控）为准。我们项目把归因字段设计为"随登录上报 + 服务器侧校验渠道合法性"，客户端只做透明转发。

返场追问: 你们打点有丢失吗？

  • 丢失场景：弱网/进程被杀。当前 BtnClickRequest 是即时上报，没有本地缓存补发。
  • 已有意识：重要事件（登录、支付档位）走协议可靠通道，按钮类事件可容忍少量丢失。
  • 优化：本地队列 + 定时批量 + 补发（见优化方向）。

优化方向（本模块）

  1. BI 上报独立协议 + 本地队列补发：解耦 BtnClickRequest，弱网不丢打点。
  2. 打点 schema 校验前置到开发期：导出时生成参数 schema，编辑器期警告。
  3. 打点面板工具：编辑器内实时显示当前会话打点流水，替代"真机+后台过滤"的验证方式。
  4. 归因模拟器增强：把 PlayerPrefs 模拟链路升级为可模拟"归因延迟/失败/渠道切换"等边界。
  5. 打点覆盖率看板：base_bi 表 vs 代码 fire 点自动比对，发现"表里有没接线"和"代码里有没上表"。
  6. token 对照表工具化：xlsx 手工维护改为从导出表+代码自动生成，消除手工同步误差。

面试官潜台词提示

  • 问"埋点体系怎么设计"→ 想听体系不是流水账：配置驱动、统一通道、口径管理、验证闭环。
  • 问"为什么这样设计"→ 必答出"打点是运营强依赖，改动主体在数据侧，代码侧只维护接线"。
  • 问"归因"→ 分层答：归因平台概念 → 我们的三层实现 → 深坑（热更时序）→ 双通路冗余设计。
  • 问"如果重新设计"→ 讲通道解耦+可靠性（补发）+ 开发期校验，展示超越现状的视野。

第 2 章 内存泄漏审计与治理

模块背景（开场一句话）

我做过两阶段全工程内存泄漏审计：Phase 1 只审 NeoFPS 插件（10 处修复），Phase 2 扩展到 C# 业务层 + Lua 层（19 个文件，11 处确认泄漏），核心发现是 Unity Material 克隆泄漏、静态集合无清理、tween 持有已销毁对象引用。这项工作的价值不在修了多少 bug，而在沉淀了一套可复用的审计方法论。

高频问题与回答要点

Q1: Unity 有哪些常见内存泄漏类型？你怎么审出来的？

回答框架：先分类，再"每类一个亲手修的案例"。

类型 1：Material/材质克隆泄漏（最高频）

  • 机制：renderer.material / renderer.materials getter 每次访问都实例化新 Material 实例（不是缓存返回），Unity 文档明确说会克隆；.material = X setter 同样每次实例化。
  • 审计手段：grep 模式签名（区分 getter/setter）扫全工程，候选点人工确认。
  • 亲手修的案例：
  • GameObjectControlPlayableAsset（Timeline 资产）：foreach 内 5 段连续 .material getter → 缓存到局部变量统一操作，DOFloat 原本跑在孤儿副本上导致动画失效。
  • FpsSingleGame 假死事件：.materials 数组 getter 拷贝整组副本，SetShaderPassEnabled 作用在副本上——原描边禁用功能一直无效。改 sharedMaterials 顺带修复功能 bug。"泄漏审计顺带挖出功能 bug"是本章面试亮点句。
  • MachineGunPlacementDetection：Update 每帧 .material = X setter 持续实例化，旧实例全泄漏 → Awake 缓存 Renderer + sharedMaterial。
  • 瞄准镜（RenderTextureScopeSRP）：OnDestroy 只销毁 RenderTexture，漏 Destroy 材质实例，瞄准镜高频路径一开一关漏一个。
  • 深度补充：为什么引擎要设计成 getter 克隆？Material 是资源级对象，直接改资源会影响所有引用者；克隆是"每 renderer 独立改色"的便利性换来隐性成本——改实例必须配对销毁，引擎不帮你回收。

类型 2：静态集合累积

  • 机制：static Dictionary/List 只增不减，跨局跨场景永不回收。
  • 案例：BuffUtils.DicBuffCreated 全代码库无 Clear，跨局累积还污染抽奖权重计算（不只是内存问题）→ FpsWorld.OnDestroy 加 Clear。"内存问题引发正确性问题"是升级版回答。
  • 深度补充：Material/Texture/Mesh 是 native 对象，C# 包装壳被 GC 但 native 侧不释放，托管 GC 管不了 native 侧，必须显式 Destroy。

类型 3：tween/委托持有已销毁对象

  • DOTween：对象销毁后 tween 仍持有引用。修复方式：缓存克隆材质 + OnUpdate 检测目标销毁后 Kill + Destroy（本项目 DOTween 版本无 SetLink，且持有方是纯 C# 类需完整限定调用）。
  • 委托链泄漏：事件订阅不退订（UI 层由框架自动清理，纯 C# 层需手动配对——见第 6 章）。

类型 4：YooAsset 资源句柄泄漏

  • 引用计数模型：handle（业务侧）→ provider（调度层）→ bundle（包裹层）逐层计数，业务 Load 创建 handle、Release 减计数，减到 0 才触发释放链；任何一环失衡该资源永不释放。
  • 泄漏形态：Load 不 Release、重复 Load 不复用、场景卸载遗漏场景专属 handle。
  • 兜底对比：强制卸载（ForceUnloadAllAssets）能兜底但不安全——会引发"使用中资源被卸载"（表现层粉块/白块）。正确姿势是配对审计而不是依赖强制卸载。

类型 5：Lua 层泄漏

  • 工具：LuaProfiler 观测 Lua.GC 曲线（分场景采样，对比进出场前后差值）。
  • 模式：闭包捕获、事件订阅不退订、全局表污染。
  • 修复案例：AnimationSystem tween 持有已销毁 obj，Lua 侧 3 处事件订阅不退订。
  • 亮点补充：审计期间 LuaProfiler 窗口数据冻结（HookLuaSetup AddComponent 返回 null），做了窗口侧兜底——审计工具自身可靠性也是审计工作的一部分。

Q2: 审计方法论——"怎么系统地找泄漏"？（本章面试价值最高）

  1. 范围切割：按程序集切（插件 → C# 业务 → Lua），每阶段出审计文档（范围/重点/清单/修复提交/变更量），同步团队，不闷头修。
  2. 模式清单驱动：五类泄漏模式各有代码模式签名，grep 签名扫全工程产生候选点。
  3. 人工确认三问（对每个候选点）：① 有没有配对清理？② 生命周期谁长谁短？③ 修复会否改变表现（sharedMaterial 影响所有引用者，需逐处确认是"误用克隆"还是"本该独立变体"）。
  4. 风险分级：HIGH（确认泄漏）/MED（模式匹配未证实）/LOW（demo 代码低风险），HIGH 优先。
  5. 验证：静态扫描解决"找全"，运行时 Profiler 曲线解决"证实"，二者不可互替。
  6. 存档纪律：审计报告独立存档，修复独立提交，不混业务改动。

Q3: sharedMaterial vs material 完整答案（口诀背熟）

维度.material getter.sharedMaterial(s)
返回每次访问实例化新实例资源本身
影响面只影响该 renderer（实例）影响所有引用该材质的 renderer
内存每次克隆0 克隆
场景真需要 per-renderer 变体时，配对 Destroy只改共享资源

口诀：默认 shared，独立变体才 material，用了必须配对销毁。

Q4: 静态集合泄漏怎么防？

  • 机制：static Dictionary/List 只增不减，跨场景累积。
  • 案例：BuffUtils.DicBuffCreated 只增不减，跨局累积污染抽奖权重 → OnDestroy 加 Clear。
  • 深度：native 对象 C# 包装壳被 GC 但 native 侧不释放，必须显式 Destroy。
  • 预防：静态集合必须写 Clear 时机注释（谁负责清、什么时候清）。
  • 反直觉点：disable domain reload 时 static 不自动清空——编辑器迭代速度优化反而引入泄漏源（面试区分度题）。

Q5: YooAsset 引用计数怎么工作？泄漏什么样？

  • 模型：handle → provider → bundle 逐层引用计数，减到 0 才释放。
  • 泄漏形态：Load 不 Release、重复 Load 不复用、场景卸载遗漏。
  • 兜底对比：强制卸载能兜底但不安全（粉块/白块），正确姿势是配对审计而非依赖强制卸载。
  • 项目事实：有整份 YooAsset handle 泄漏审计文档（按 provider 维度盘点不配对点）。

Q6: Lua 层泄漏怎么找？

  • 工具：LuaProfiler 分场景采样 Lua.GC 曲线。
  • 模式：闭包捕获、订阅不退订、全局表污染。
  • 亮点句：审计工具自身可靠性也是审计工作的一部分（LuaProfiler 兜底修复）。

第 3 章 死代码扫描与清理

模块背景（开场一句话）

我做过全工程死代码扫描与分批清理：Lua 侧识别死文件 71 个、空壳 43 个、生成残留 151 个，C# 侧识别 33 个、疑似 21 个。这项工作的面试价值在方法论——动态语言死代码判定是普适难题，"静态扫描找全 + 运行时验证证实"的双轮法可迁移到任何动态语言项目。

高频问题与回答要点

Q1: 死代码为什么要清？留着不行吗？

先立论再讲做法：

  • 认知成本：死代码是负资产——读代码的人要花时间判断"这有人调吗"，团队越大越贵。
  • 误导修改：改功能时容易改到无人使用的分支，浪费并引入回归风险。
  • 热更脚本体积：本项目 Lua 全热更，脚本体积直接进热更包。
  • 下线残留堆积：下线玩法（美女/故事系统，69+1 文件删除 + 68 个 lua 大改）若不清，下一个下线玩法继续堆。
  • 生成物残留：Luban 导出物中源表已删的死表残留 11 个，误导查表。

Q2: Lua 是动态语言，死代码怎么判定？（核心题）

先讲难点：C# 可靠编译器/IDE Find Usages，Lua 不可 100% 静态判定——加载点可以是字符串拼接、配置驱动加载、FSM 状态拼接、UI 名即文件名，任何字符串间接层都会漏判/误判。

我的方案：动态加载点清单法

  1. 枚举动态加载点清单（关键创新，面试重点讲这里）：把全工程"通过字符串间接找到文件"的加载点枚举成清单：
  • UI：UIManager:OpenUI(name)，UI 名即文件名，还有 FairyGUI 组件名。
  • Scene：场景脚本文件名=场景名。
  • 配置驱动：引导配置引用文件名。
  • FSM 状态拼接："MainBuildingBubbleStates." .. stateName 字符串拼接类名。
  • 反射（C# 侧）。
  1. 双验证规则：0 引用 且 不在任何动态加载点覆盖范围内 → 判死。
  2. C# 侧加类名+GUID 双验证：.meta 的 GUID 可能被 prefab/asset 引用。
  3. 分批清理：逐批 commit 注明行数与验证方式（如"删除 NamePool.lua（3008 行，全工程 0 引用）"），出现回归可单批回滚。
  4. 扫描脚本可复跑：dead_code_scan.js / dead_code_classify.js / dead_code_final.json 保留在 .omc/artifacts，2026-09-30 基线可复跑比对。

TSD 加密环境特有约束（详见第 9 章，此处一句带过）：bash 裸 grep 看到的是密文，node/git 看明文——扫描脚本必须用 node 写，"工具选型受环境约束"本身就是面试素材。

Q3: 怎么防误删？

  • 双验证：0 引用 + 动态加载点清单覆盖；C# 加类名+GUID 双验证。
  • 分批清理：逐批 commit 注明行数与验证方式，回归可单批回滚。
  • 回滚预案：靠 git 回滚，不靠临时备份（备份会漂移，git 保真）。
  • 生成物不手改：Luban 导出物只经导出管线变更，防"源表删了生成物残留"误导。
  • 删前复跑：删除前复跑扫描并比对基线。

Q4: 清理收益怎么量化？

  • 脚本体积：Lua 全热更，脚本体积直接进热更包，清理=直接收益。
  • 认知成本：71 个 0 引用文件 = 71 次"这有人调吗"的判断成本清零。
  • 生成残留：11 个死表残留清掉后查表不误导。
  • 大文件案例：NamePool.lua 3008 行 0 引用、promise_spec 1620 行框架测试 0 引用、FairyBook 610 行 0 引用。
  • 严谨句式："识别 ≠ 已清理"——C# 识别 33 + 疑似 21 是识别数，不是全部已清数。

Q5: 怎么防"清了又长"？

  • 源头治理：玩法下线时同步清代码（美女/故事系统下线同步改 68 个 lua）。
  • 保留兼容层：下线时保留必要兼容常量（GIFT_SHOP_BUILD_BEAUTY、EXPLORE_PARAMETER_FUNGUS），兼容层也要有"何时可删"的判断。
  • 定期大扫除模式：当前是人工定期扫，未进 CI——如实承认，引出优化方向。

第 6 章 UI 框架与 FairyGUI

模块背景（开场一句话）

UI 层问题治理：响应式绑定失效、合批缓存、对象池回收、网络遮罩体验。面试价值：对响应式数据绑定框架的失效模式有体系化认知。

Q1: 响应式绑定读旧值（主故事）

  • 现象：全局状态切换类 bug，UI 显示非最新数据。
  • 根因两层：① Refresh 是死标志（update=true 无消费者，看似刷新了实际没执行）；② VM.hashset 绑定旧表引用，SyncXxx 整体换表后绑定链失效，UI 读旧数据。
  • 修复：在同步层（DataMediator SyncXxx）fire 事件，UI 订阅同步层事件而非依赖绑定链。
  • 实例：改装车主界面战力与额外加成不刷新（1a63f142a5 / d207e95）。
  • 泛化句："数据换了引用，绑定还指旧引用"是响应式框架的经典失效模式；"Refresh 是死标志——看似刷新了实际没执行"。

Q2: TimerSystem.Register 签名坑

  • 签名 Register(name, 延时秒, fn)；裸 (0.2, fn) 静默不执行——不报错不执行，只有"功能没发生"，最危险。
  • 规则：跨 UI 生命周期的延时用全局 Timer + 带 name；UI 内延时用 self:StartTimer（自动清理）。UI 关后弹窗仍要显示的场景必须走全局 Timer。
  • 泛化句：静默失败是最危险的失败模式，只能靠测试兜底。

Q3: FairyGUI 合批缓存（invalidateBatchingEveryFrame）

  • 真机上 alpha 动效期间合批缓存导致 StateGroup 子内容不显示——编辑器看不出来，真机才复现。
  • 修复：动效期间开启 invalidateBatchingEveryFrame（ba103c5e22）。
  • 泛化句：编辑器与真机渲染差异类问题的排查意识。

Q4: 对象池回收拦截漏洞（62ed6a3151）

  • GObjectPool 回收路径存在拦截漏洞，修复后回收路径与其他路径行为一致。
  • 泛化句：对象池的坑都在"回收路径"，不在"取用路径"。

Q5: 网络遮罩体验优化（cda5e5fa4c）

  • 联盟主界面为顶层 UI 时，联盟领地/礼物请求不再弹网络遮罩 UINetWaiting。
  • 泛化句：体验类需求本质是"遮罩的必要性分级"，按 UI 层级与操作上下文分级弹遮罩。

优化方向（本模块）

  1. 响应式绑定失效静态检查（绑定链 lint）。
  2. Timer 签名静态检查进 luacheck 规则（裸两参调用报警）。
  3. 真机渲染差异问题 checklist（动效/合批/mask 链路）。

本章核心记忆点

  • 响应式失效模式："数据换了引用，绑定还指旧引用"；Refresh 死标志。
  • Timer 裸两参 = 静默失败，最危险的失败模式。
  • 真机渲染差异：合批缓存问题编辑器看不到。
  • 对象池的坑在回收路径。

第 7 章 渠道 SDK 与登录链路

模块背景

多渠道包体系：游龙渠道账号隔离、审核包屏蔽逻辑、FCM 通知崩溃修复、服务器列表状态显示、登录 UI 流程优化。本章面试价值：渠道化改造的难点不在"加开关"，而在读写侧一致性与盲区识别。

Q1: 游龙账号隔离（主故事）

  • 需求：同一设备上，渠道包与主包账号相互隔离，避免账号串用。
  • 方案：Passport/DeviceId 的读侧统一加 _YL 后缀（commit 08209006af）。
  • 盲区：读侧统一后，写侧（邮箱注册/绑定/切换/解绑 4 处 HTTP 出口）未过 ApplyChannelSuffix，导致账号凭据读写不一致。补盲区提交后因引入新问题又 revert（4aa20277ff）——工程判断："风险收益比不划算时先恢复稳定，问题另开任务"。
  • 特例先行：游客账号（#_#visitor 结尾）不追加后缀（c7f27ef0fd）——隔离规则先枚举特例再定通则，避免先写通则再打补丁。
  • 另一坑：该后缀匹配用的 Lua pattern 不支持可选组量词（如 (?:...)?），匹配逻辑要绕开写。

泛化句：渠道化改造的本质是"读写侧一致性工程"，加开关只是第一步。

Q2: FCM 通知崩溃修复

  • 现象：Android 8/9 设备收到 FCM 通知即 NoSuchMethodError 崩溃。
  • 定位：androidx.core 版本过低。
  • 修复演进两步：先强制 1.9.0 修崩溃（3f3967988f），后抬到 1.13.1 满足 compileSdk>=34/targetSdk=36（64cf3f8991）——版本对齐是持续过程，不是一次性。

泛化句：安卓依赖冲突排查走 gradle 依赖树，修复要考虑 targetSdk 演进。

Q3: 服务器列表状态显示

  • 新增服务器状态图标（0 未开放 / 1 拥挤 / 2 正常 / 3 推荐+角标 / 4 爆满），爆满服禁止进入并弹提示。
  • 文案走本地化 key（SERVER_COMMON_STATUS_TEXT_x）。

泛化句：状态枚举驱动 UI，禁止文案硬编码，统一走 _L("KEY")。

Q4: 审核包与渠道开关

  • 审核包屏蔽：审核期间不判断宝石数量（审核合规要求）。
  • ANTI_ADDICTION 渠道：UILoading 隐藏 GmBtn/AccountBtn，屏蔽账号与第三方登录入口。

泛化句：审核包是"临时形态"，屏蔽点要集中管理，避免散落 hard-code。

深水区追问

  1. 账号隔离为什么写侧会漏？

答：读侧改动点集中（Passport 读属性一处收口），写侧出口分散（多处 HTTP 请求构造点），改动半径不对称——集中/分散不对称是盲区产生的结构性原因。

  1. revert 后问题怎么收尾？

  1. 渠道屏蔽点集中配置化（渠道能力矩阵表驱动，按渠道×能力查表）。
  2. 账号后缀读写侧一致性测试用例（注册→读取互验、绑定→读取互验）。
  3. gradle 依赖审计自动化（依赖树 diff 报告，CI 阶段拦截版本漂移）。

本章核心记忆点

  • 渠道化 = 读写侧一致性工程；集中/分散不对称产生盲区。
  • 特例先行：先枚举特例（游客账号）再定通则。
  • revert 也是工程决策，不丢人，关键是收尾路径。

第 8 章 BGM 与音效系统

模块背景

主城 BGM 状态机治理与音效接入规范化。表现系统（音乐/音效）与业务状态的联动看似只是"细节打磨"，实则考验通用设计能力与工程习惯——面试官常用这类话题考察你是否能把个例需求沉淀为可复用的机制。

Q1: CityBGMPlugin — 演出类 UI 与 BGM 互斥

需求最初是个例：某个 UI 打开时停主城 BGM，关闭后恢复。随后同类需求反复出现（别墅升级奖励弹窗等），我们在第三次出现之前把它抽成了通用插件 CityBGMPlugin：演出类 UI 打开时静音，关闭时恢复主城 BGM；同时提取 SceneManager.StopCityBGM 作为统一停播入口。

这一步的关键收益是消除了"每个 UI 自己停"的不一致——原先散落在各处的停播调用，行为细节各有偏差，统一入口后互斥规则只有一份实现。

泛化句：同一需求出现第三次之前，就该抽成通用能力。一次需求=实现，两次=抽象候选，三次=抽象。

Q2: 陨石危机 BGM 卡压力音乐

现象：陨石危机活动 UI 关闭后，压力音乐一直不切回祥和主城 BGM，直到重登才恢复。

根因：BGM 切换判定依赖服务器回推的 RewardCount=5，但该会话服务器不回推这条消息，判定恒不成立，压力状态永远无法结束。

修复分三层：第 5 次攻击时 SetFinalState 写入本地终态标记 meteorFinishedLocally；IsPressureEventGoing / IsMeteorCrisisFinished 增加兜底判定，不单纯依赖服务器状态；关闭 UI 时 TryShowRatingIfFinished 补一次 fire，保证收尾事件不丢。

后续又做了去硬编码：攻击次数、终态判定、动画名、领满判定统一改为读 base_pressure_main 的奖励数上限（#ARRAYINT_REWARD），并加 config 判空早退，配置缺失时不走异常路径。

泛化句：依赖服务器回推的状态，要用本地终态标记兜底——服务器状态不可信时，客户端要能自洽收敛。

Q3: 开场 CG 与 BGM 时序

现象：新号开场 CG（svs.mp4）还没播完，主城 BGM 已经响起，视频音乐被顶掉，首因体验很差。

修复：loading 完成后主城 BGM 挂起，等 CG 播完或被跳过后，由 UIGuideVideo 负责恢复；同时用 IsTriggerComplete(800002) 做兜底放行，让跳过开场的老手账号不会被永久卡在静音状态。

泛化句：媒体播放（视频/音乐）的冲突要走统一的挂起-恢复协议，不能各播各的。

Q4: 音效接入规范化（sfx-creator skill）

音效接入是高频重复工作，我们把它沉淀为 skill：文件入库规范 → config.toml.txt 注册 event → Lua 侧 AudioSystem:PostEvent 接线 → 时长判断与 mode 选择。资源收集音效另有专用流程 collect-audio-creator（含 MediatorItem 的 resourceAudio 映射）。

实例：红包打开音效 RedEnvelopeOpen event，在四类红包领取成功（GET_RED_ENVELOP_REWARD_RESULT）处单点触发，改动集中、回归面小。

几个值得讲的工程细节：

  • 音效防连点：高频点击 UI 时避免同帧叠加播放。
  • 批量替换 33 个同名音效时，meta 中关闭 forceToMono 和 normalize，保留原始立体声与响度，避免保真度损失。
  • 快速战斗胜利音效曾改为"等服务器回调再播"，后来 revert 改回立即播。时序与体验的权衡没有绝对正确，验证方式决定选择——能验证什么，就按什么标准取舍。

深水区追问

1. BGM 状态机怎么设计？

单一 BGM 所有权 + 挂起-恢复协议 + 本地终态兜底。核心原则是谁占用谁释放：任何时刻只有一个 BGM 持有者，挂起方退出时恢复上一个状态，服务器状态缺失时由本地标记收敛。

2. 为什么不用 Wwise/FMOD 类中间件？

本项目用事件驱动（PostEvent），规范化点在"注册-接线-验证"三步，这套流程与具体中间件无关；换中间件只需要替换底层播放实现，接入规范不变。

优化方向

  1. BGM 状态可视化：编辑器内实时显示当前占用者与挂起栈，排查音乐不切换类问题不再靠翻日志。
  2. 音效注册自动化：文件入库时自动生成 event 注册与映射，消灭手工注册漏配。
  3. 音效回归清单自动化：版本出包前跑一遍音效 spot-check 清单，防止替换/重命名引发的静默丢失。

本章核心记忆点

  • 三次法则：同一需求第三次出现前抽成通用能力（CityBGMPlugin）。
  • 本地终态标记兜底：服务器状态不可信时，客户端要能自洽收敛。
  • 媒体播放统一挂起-恢复协议，谁占用谁释放。

第 9 章 工程工具链与环境适配

Q1: TSD 透明加密环境的开发适配（本章主故事）

  • 环境特征：企业透明加密，整树磁盘密文；按进程白名单解密——node/git/claude 看明文，PowerShell/cmd 看密文；解密后过一段时间复密。

  4. git push 外网被拦（curl 55）：走 GitHub Git Data API 兜底通道（push_via_api.js），用 API 建 commit/tree/ref 绕过网络层拦截。

Q3: 交互式配置生成工具（genLua/genLuaUI）

第 10 章 通用 Unity/Lua 题的项目化回答

面试官问通用基础题时，用项目经历把答案"落地"，区分度立刻不同。本章给每类通用题一个"项目化锚点"。

Q1: GC 优化怎么做过？

  • 项目锚点：性能规范——VM.hashset/VM.array 用于大集合、对象池复用+Clear()、循环内禁字符串拼接用 StringBuilder、避免 LINQ/foreach（旧 Unity）。
  • 项目化答法：不只背"GC 原理"，而是说"我们项目的性能规范第一条就是……，落地案例是改装车界面防连点+对象池"。
  • 补充：Lua 侧 GC 压力靠 LuaProfiler 分场景采样监控（见第 2 章）。

Q2: 热更原理？HybridCLR 和 XLua 的区别？

  • 锚点：本项目 C# 用 HybridCLR、逻辑热更用 XLua。
  • 一句话区别：HybridCLR 是 C# 解释执行方案（补充元数据+解释器），XLua 是 Lua 绑定方案——前者热更 C# 代码本身，后者热更 Lua 脚本。
  • 项目化深挖点：双热更体系的时序问题是真实踩过的坑——桥接方法在热更程序集，任何依赖它的调用必须等 LoadDll 完成后（_G.Root.DllEntry 门禁，见第 1 章）。
  • 泛化句：热更体系面试的核心不是背原理，是讲"热更时序"这个工程难点。

Q3: Update 里该做什么/不该做什么？

  • 锚点：本项目 ECS/System 架构，System 生命周期由框架驱动，控制器框架缓存，不手动缓存。
  • 项目化答法：讲"事件驱动替代轮询"的实际案例——BGM 切换靠事件/终态标记而非每帧查询（第 8 章）。

Q4: xpcall 保护？

  • 锚点：XLua 下 C# 调 Lua 必须有 xpcall 保护，错误回传 C# 侧日志；本项目调试规范"追踪完整调用链再提修复"。
  • 泛化句：xpcall 是"错误可观测性"的一部分，不只是防崩。

Q5: FairyGUI 和 UGUI 的区别？

  • 锚点：本项目 FairyGUI + GObjectPool。
  • 要点：FairyGUI 编辑器驱动+GObject 池化；合批机制差异（invalidateBatchingEveryFrame 案例，第 6 章）；Prefab 坐标转换用 FairyGUI API（LocalToGlobal/LocalToRoot）而非 Unity API。
  • 泛化句：UI 框架选型的面试答案是"讲清失效模式"而不是"讲清优点"。

Q6: 资源管理怎么做？

  • 锚点：YooAssets 引用计数（handle→provider→bundle 释放链）+ Luban 配置表体系（Excel→导出→Configs.base_xxx.Hash[]/INT_GROUP.In(x).Rows 查询）。
  • 项目化答法：引用计数失衡的泄漏形态与配对审计（第 2 章）+ 配置表"导出物只读"纪律。

深水区追问

  1. "你们 GC 优化收益多少？"——如实答：有性能规范与 Profiler 验证流程，无精确收益数字；诚实比编数字安全。
  2. "HybridCLR 补充元数据的原理？"——AOT 泛型/反射调用缺失元数据由解释器补齐；答出"易变代码进热更程序集，AOT 侧只留稳定壳"的工程经验。

通用答法模板

  1. 定义（一句）→ 2. 项目锚点（我们怎么做/踩过什么坑）→ 3. 泛化句（可迁移的方法论）。三段式，30 秒内完成。

本章核心记忆点

  • 通用题+项目锚点=区分度。
  • 双热更体系的时序门禁是最有项目味的深挖点。
  • 诚实答"没有精确数字"优于编造。

第 11 章 优化方向汇总（跨模块路线图）

各章优化方向的汇总与优先级排序。面试收尾问"接下来想做什么"时，从这里取材——优化方向要能说出"为什么排这个优先级"。

优先级排序原则

  1. 事故驱动优先：曾引发线上问题的方向优先（重登类时序、内存基线）。
  2. 复利优先：工具化/skill 化收益随时间累积（扫描 CI 化、日报自动化）。
  3. 低耦合优先：不依赖跨团队协调的先做。

一、质量防线类（事故驱动）

  1. 内存基线看板：分机型分场景 PSS/mono heap 双基线自动比对，超基线报警（第 2 章）。
  2. 死代码扫描 CI 化：合入后自动重扫，新增死代码 PR 阶段报警（第 3 章）。
  3. 导表校验：引导 ID 引用完整性校验进导表管线（第 4 章 Config431 案例）。
  4. BI 打点 schema 校验前置：导出时生成参数 schema，开发期警告（第 1 章）。

二、效率工具类（复利）

  1. 打点面板工具：编辑器内实时打点流水，替代"真机+后台过滤"验证。
  2. MissionGraph 可视化编辑器：消除手工 YAML 编辑（配置驱动的代价转移给了程序——工具化把代价拿回来）。
  3. 引导状态 inspection + 快进/回放。
  4. skill 矩阵扩展：code review checklist、打包状态查询。

三、架构演进类（低耦合）

  1. BI 上报独立协议 + 本地队列补发（弱网不丢打点）。
  2. AI 行为节点超时框架化（所有 Act 节点统一超时与失败态）。
  3. 表现资源生命周期联动清理框架（退出/跳过路径也清 AOE/timeline）。
  4. 渠道能力矩阵表驱动（屏蔽点集中配置化）。

面试收尾话术

"短期内我会优先做质量防线的 CI 化——内存基线和死代码扫描这两个已经在手工跑、被验证过有效的东西自动化；中期做 MissionGraph 编辑器这类把配置驱动代价拿回来的工具；长期看 BI 通道解耦这类架构演进。排序逻辑是事故驱动 > 复利 > 低耦合。"

本章核心记忆点

  • 优化方向=事故驱动+复利+低耦合三个排序原则。
  • 收尾话术三段式：短期质量防线 → 中期工具 → 长期架构。
